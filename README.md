# あなたの町の直売所

無人直売所の「今日、何があるか分からない」を解決するWebアプリです。
生産者が写真1枚で出荷状況を投稿し、消費者が近くの直売所を計画的に訪れられるようにします。

**https://direct-sale-store.onrender.com**

## なぜ作ったのか

田舎生まれ田舎育ちの私。なんでも揃うスーパーまでは、車で30分程度かかります。
そんな私にとって、野菜の無人市（直売所）は重要な食料の調達先です。

ただ、直売所は今日何を売っているかがわからない。
だから、必要なものはスーパーで購入して、「直売所に何かいいものがあればラッキー」という存在になっていました。

比較的安価に新鮮な野菜が買える直売所で、必要な野菜を買えればいいのに。
今日何が出荷されているかを知らせてくれたら、と常々感じていました。

その裏には、もう少し大きな問題もあると考えています。

日本の食料自給率という社会課題の根底には、生産者が利益を得て農業を継続できるかという問題があります。
無人直売所は生産者にとって比較的利益率が高い販路であると思えるのと、手軽に始められる商売でもある。
それなのに「今日の出荷状況が分からない」という理由だけで、消費者の買い物計画から外れてしまっている。

生産者が利益を出せれば、農業に従事する人、小遣いレベルでも農業で商売をしようとする人が増えるかもしれない。
それは日本の食料自給率を、少しでも上げることに寄与するのではないか。

そう考えて、このアプリを作りました。

## このアプリが目指す好循環

\```
消費者が購買計画に直売所を入れる
        ↓
直売所での消費が増える
        ↓
生産者は利益率の高い直売所で利益を得る
        ↓
もっと出荷しよう、と考える
        ↓
「それなら自分も」と直売所を始める人が増える
        ↓
生産が増える
\```

## 誰のためのアプリか

### 生産者（投稿する側）

無人直売所を運営する、65歳以上中心の個人農家。

日本の農業従事者の約7割は65歳以上です。
スマホは持っているし、LINEも使える。でも、SNSで「発信する」という経験はほとんどない。

この人たちが、迷わず投稿できるかどうか。それがこのアプリの成否を分けると考えました。

### 消費者（見る側）

直売所が好きで、車移動中に見かけたら立ち寄る習慣がある層。
健康にも気を使い、できれば新鮮な野菜を摂りたいと思っている40〜60代の住民。

すでに直売所の価値は知っている。でも、購買計画には組み込みづらいと感じている人たちです。

## 一番こだわったこと

**「投稿する側」を主役にしたUIにすること。**

既存の類似サービスを調べていて気づいたのは、多くが「見る側」の目線に偏っているということでした。
でも、生産者が投稿してくれなければ、このアプリには何の価値も生まれません。

だから、こうしました。

- ヘッダーやフッターの小さなアイコンに、投稿導線を頼らない
- **トップページを開いた瞬間、投稿ボタンが目に入る配置にする**
- 「ログイン」「アカウント」のような言葉を使わず、「登録」「今日の出荷状況を投稿する」と書く
- パスワードという概念を作らない（電話番号 + SMS認証のみ）
- 投稿は写真1枚で完結する。詳しく書きたい人だけ、折りたたみを開けばいい

高齢の方はパスワードが苦手、という記事を読んだことがあったので、認証方式もそこから逆算しました。

もう一つ、SNSをあまり使わない生産者を想定して、**アプリの利用を促す宣伝用ポスターを印刷できる機能**も用意しています。
デジタルだけで完結させず、直売所の現場に紙で貼れるようにしたかったからです。

## 主な機能

### 生産者向け

| 機能 | 内容 |
|---|---|
| 登録・ログイン | 電話番号 + SMS認証（パスワード不要） |
| 店舗登録 | 店の前でボタンを押すだけで、GPSから位置を取得 |
| 出荷投稿 | 写真1枚で投稿完了。任意項目は折りたたみの中 |
| 使い方の印刷 | 登録・投稿の手順、宣伝用ポスターを印刷できる |

### 消費者向け

| 機能 | 内容 |
|---|---|
| 直売所を探す | 一覧表示、および現在地からの距離順ソート |
| 店舗詳細 | その店の情報と、出荷状況の履歴 |
| 最近の投稿 | トップページに最新10件を表示 |

## 技術的に苦労したところ

### SMS認証（Twilio Verify）

外部APIを実装するのは初めてで、しかもサービスが海外のものだったため、使い方を読み解くのにかなり苦労しました。

さらに詰まったのが、**電話番号の形式の食い違い**です。

- Twilioに送るときは `+819012345678`（国際形式）
- しかし`User`モデルのバリデーションは `/\A\d{11}\z/`（11桁の数字のみ）

この2つを別々のタイミングで実装したため、認証は通るのに保存できない、という状態になっていました。
コンソールで`user.errors.full_messages`を確認して、ようやく原因にたどり着きました。

### 位置情報とJavaScript

「JSでパラメータを送る方法」をずっと調べていたのですが、
実はこれ、**URLの書き方の話**でした。

\```javascript
window.location.href = `/shops/index_distance?current_latitude=${lat}&current_longitude=${lng}`
\```

`?` はURLの決まりごとで「ここからパラメータです」と示すもの。
JSの文法をいくら調べても出てこないはずでした。この気づきは大きかったです。

## 設計判断で「あえて選ばなかった」こと

締切との兼ね合いで、意図的に見送った判断があります。

### Active Storage → CarrierWave

Railsの標準機能であるActive Storageを使う選択肢もありましたが、
残りの日数から逆算すると、他にも時間がかかる工程があり、学習コストをかけられませんでした。
これまで学習していたCarrierWaveを採用しています。

### 複数枚投稿 → 1枚に絞る

`accepts_nested_attributes_for`を使い、最大3枚まで投稿できるところまで実装していました。
しかし、複数枚のプレビュー表示（JS）まで含めると時間がかかりすぎると判断。

**モデル・テーブル設計は複数枚対応のまま残しつつ、フォームだけを1枚に絞りました。**
将来、複数枚に戻すときに、設計をやり直さなくて済むようにしています。

### 距離順の実装

「1つのindexアクションの中で条件分岐する」という書き方も検討しましたが、
今の自分にとって確実に実装できる方法を優先し、`index_distance`という別アクションを新設しました。

技術的な美しさより、動くものを確実に仕上げることを選びました。
